# 改进说明

本轮针对"能跑通"之外的稳定性、统计诚实性与可证明性做的一轮加固。每条都写清
**问题 → 做法 → 验证**，方便面试时逐条讲，也方便以后回看为什么这么改。

测试数量：46 → **69**（新增 `tests/test_improvements.py` 23 项）。

---

## 一、会话不再"重启就失忆"

**问题**：会话只存在内存字典里，且只增不减。前端把 `session_id` 存在 localStorage，
服务重启后带着同一个 id 追问，拿到的是一个空白会话——数据库里明明有历史，模型却重新问"请提供成绩"。

**做法**（`app/session.py`）
- `SessionStore.get_or_create` 未命中时按 id 去数据库回填（`db.list_session_records` → `restore_from_records`），对话文本与最近一次数据集一起恢复；
- 容量上限 200（LRU），空闲 2 小时清理，避免长跑内存无界增长；
- 每个 `Session` 一把锁，同一会话的并发请求串行执行，防止两条消息交错写进 `messages`；
- `/api/health` 暴露 `sessions.in_memory / restored_from_db`，能看出回填是否生效。

**验证**：`test_missing_session_is_restored_from_db`、`test_lru_evicts_oldest`、`test_ttl_sweeps_idle_sessions`。

## 二、模型接口的抖动不再直接变成"失败记录"

**问题**：`max_retries=0`。429 限流、连接闪断、超时都是瞬时故障，一次就把整轮对话判死，
用户看到红色失败卡片——演示时模型一抽风就等于系统挂了。

**做法**（`app/llm.py`）
- 只对**瞬时故障**（429 / 超时 / 连接失败 / 5xx）做 2 次指数退避（0.8s、1.6s）；
- 鉴权失败、4xx 参数错误不重试，立即报错——重试没有意义；
- `LLMError` 增加 `code`（`AUTH/RATE_LIMIT/TIMEOUT/CONNECTION/SERVER/API_ERROR/ROUNDS/SCHEMA/EMPTY`），随响应下发；
- 实际重试次数写进运行日志的 `retries` 字段，能区分"模型慢"还是"网络抖"。

**验证**：`test_retry_rate_limit_then_success`（两次故障后成功，共 3 次调用）、
`test_retry_stops_after_max_attempts`（用尽后抛 `TIMEOUT`）、`test_auth_error_is_not_retried`（401 只调一次）。

## 三、限制条件由程序兜底，不再"模型说什么算什么"

**问题**：工具已经算出"样本只有 2 个点""R² 偏低""属于外推""预测区间"，但 `limitations`
只被校验"至少一条非空"。模型写一句"样本较小"就能过关，用户看不到真正的不确定性来源。

**做法**（`app/agent.py:_merge_tool_warnings`）
- 结构化校验通过后，程序把工具 `warnings` 强制并入 `limitations`：**模型只能加，不能减**；
- 跳过写给模型看的指令型文案（如"结论中应说明…"），并按主题去重（外推/预测区间/R²/样本/相关），避免同一件事说两遍；
- 追加行为写入日志 `limitations_merged`，可回溯。

**验证**：`test_tool_warning_is_appended`、`test_same_topic_is_not_repeated`、
`test_instruction_style_warning_is_skipped`、`test_warnings_are_merged_end_to_end`。

## 四、预测从"一个精确数字"变成"区间"

**问题**：4 个点外推第 5 次，只给"91.5 分"，看起来像确定值。实际上外推误差随距离放大，
只给点估计是过度自信。

**做法**（`app/tools/trend.py`）
- 用残差标准误算 95% 预测区间：`ŷ ± t(0.975, n-2)·s·sqrt(1 + 1/n + (x₀-x̄)²/Sxx)`；
- t 临界值用查表（自由度 1—30，超过取 1.96），不引入 scipy，便于逐行核对；
- n=2 时不给区间（残差自由度为 0），沿用"两点必成直线"的告警；
- 图表在预测点画误差棒并标注 `95%: 88.86—94.14`，一眼能看出这是范围；
- 区间写入数据库（`pred_low/pred_high`），历史记录详情里也能看到。

**验证**：`test_interval_wraps_prediction`（含手算核对）、`test_two_points_have_no_interval`、
`test_interval_is_persisted_with_record`。

**实测**：四次 78/82/85/88 → 斜率 +3.3、R²≈0.99、第 5 次 91.5 分，**95% 区间 88.86—94.14**。

## 五、检索从"凭感觉"变成"有评估集"

**问题**：覆盖率阈值 0.34、余弦阈值 0.10 是试出来的，被问"怎么定的"只能答"调出来的"。

**做法**
- 新增 `eval/retrieval_cases.json`：26 条（20 条应命中并指定文件、6 条应返回空）；
- 新增 `scripts/eval_retrieval.py`：算 recall@k、命中平均排名、负例误报，并扫描"覆盖率 × 余弦"门槛；
- 顺手修了两个真实缺陷：`R²` 这类"单字母+上标"会被分词器整体丢掉；口语化提问（"突然掉了20分"）词汇与资料对不上。
- 引入**兜底式查询扩展**：只在原话零命中时才用同义词表重试一次——一开始就扩展会把本来排第一的正确片段挤下去（"如何提高复习效率"踩过）。

**结果**：recall@3 从 80% → **100%**，命中平均排名 1.0，负例误报 **0/6**。
门槛扫描显示 (0.34, 0.10) 正是"误报 0 且 recall 最高"的那一档，不是拍脑袋定的。

**验证**：`test_recall_and_false_positive_rate`（召回低于 90% 或出现误报就失败）、
`test_r2_query_is_searchable`、`test_paraphrase_falls_back_to_expansion`。
详见 `docs/检索评估.md`。

## 六、有成绩又要建议时，必须检索一次资料

**问题**：`"我成绩 78、82、85，怎么提高"` 同时需要拟合与资料，但系统提示是两条独立规则，
模型有时只拟合就给建议，容易变成"多刷题、多总结"的空话。

**做法**：模型准备直接作答、但本轮没检索、且用户问的是"怎么/为什么/提高/方法"时，
由程序补一次 `search_study_knowledge`，把命中片段作为 system 消息插进上下文让它重答；
命中为空则要求它明说"资料不足"。只补一次，不会形成循环。

## 七、十几秒的等待有进度了（SSE）

**问题**：一次分析要走"理解 → 调工具 → 校验 → 可能修复"，十几秒页面只有转圈。

**做法**
- `handle_message` 增加 `progress` 回调，在思考/调工具/工具完成/修复各阶段推事件；
- 新增 `POST /api/chat/stream`（SSE），后台线程跑 Agent，事件经队列推给前端；
- 前端优先走流式，显示"正在拟合成绩趋势…""正在检索本地资料…"等真实阶段；
  **流式不可用时自动回退** `/api/chat`，接口挂了也不影响对话。

**验证**：`test_phases_are_emitted_in_order`（thinking → tool → tool_done 顺序正确）、
`test_progress_callback_failure_does_not_break_chat`（前端断开不影响结果）。
实测 SSE 输出：`start → thinking(round 1) → tool(trend) → tool_done → tool(检索) → tool_done → thinking(round 2) → result`。

## 八、日志与数据库的小修

- **日志轮转**：`run.jsonl` 超过 8MB 自动改名为 `run-时间戳.jsonl`，`run.jsonl` 仍是"当前日志"，历史报错信息里的路径写法依然有效；
- **会话索引**：`analyses(session_id, id)` 建索引，按会话取轮次/删会话不再全表扫；
- **搜索转义**：`LIKE` 里的 `%` `_` 现在会转义——以前搜一个 `%` 会把全部记录都命中；
- **多关键词**：空格分隔的多个词要求全部出现（AND），不再当成一个长串匹配。

**验证**：`test_like_wildcard_is_escaped`、`test_multi_keyword_requires_all_terms`、`test_session_index_exists`。

## 没有改的部分（有意为之）

- **没上 FTS5**：SQLite 的 trigram 分词要求每个词 ≥3 字符，而中文常用词多为 2 字（"成绩""波动"），
  上了反而降低召回；当前库只有百来条记录，`LIKE` 全表扫的代价可以忽略。数据量上去再换。
- **没做多科目/多数据集**：属于产品范围扩张，会牵动工具契约与会话结构，不适合在交付前动。
